## 问题类型（评测集的核心设计）

不只测「字幕能答的问题」，而是**覆盖能力边界**，让不同架构的差距显性化：

| 类型 | 定义 | 考察 | 需要视觉 |
|---|---|---|---|
| `single_hop` | 答案在单段字幕中直接可答 | 基础检索 | ❌ |
| `multi_hop` | 需综合多段字幕 | 跨片段检索+综合 | ❌ |
| `visual_only` | 答案只在画面里，字幕没有 | 视觉理解 | ✅ |
| `joint` | 需字幕 + 画面结合 | 多模态联合 | ✅ |
| `unanswerable` | 视频根本没讲过，应拒答 | 幻觉抑制 | 视情况 |

**示例**：
- `visual_only`：「主讲人身上穿的短袖 T 恤是什么颜色？」
- `unanswerable`：「主讲人佩戴的眼镜是什么品牌？」

这类问题**只看字幕的系统和多模态系统的差距会立刻显现**。

## 数据格式

```

├── eval_retrieval.py     # 检索层评测（Recall@K / MRR）

├── retry_failed.py       # 重试裁判失败的记录

```

## 评测结果（v4，2026-09-13）

> ⚠️ **v4 相对 v3 是换了裁判模型后的整体重跑。** 此前裁判用的就是被评模型
> （deepseek，自评偏差）；现改用独立的 `glm-5.3-flash`（智谱）。
> **换裁判后 64 题里 42 题的分数变了**（系统性偏移，不是抖动）——
> 也就是说**分数尺度是由裁判模型定义的**，v3 及更早的数字与本节不可直接比较。
> 详见文末「修订记录」与「已知局限」。
>
> 更早的两次方向性修正（v2 字幕修正、v3 指标口径）同样记录在修订记录里。

### V1：纯字幕 RAG（检索 Top5 → LLM 生成）

**检索层**

`multi_hop` 的 `time_start`/`time_end` 为**并列列表**（按索引一一对应多个答案片段），
因此额外报告**片段覆盖率**与**全片段命中率**。

| 问题类型 | R@1 | R@5 | MRR | 片段覆盖 | 全片段命中 | 严R@5 |
|---|---|---|---|---|---|---|
| single_hop | 0.375 | 0.750 | 0.552 | 0.750 | 0.750 | 0.688 |
| multi_hop | 0.562 | **0.938** | 0.729 | 0.707 | **0.500** | 0.750 |
| joint | 0.375 | 0.562 | 0.453 | 0.562 | 0.562 | 0.375 |
| visual_only | 0.438 | 0.562 | 0.500 | 0.562 | 0.562 | 0.500 |
| **主战场合计**（前 3 类） | 0.437 | **0.750** | 0.578 | | | |

> **`严R@5`** 是新增的严格判据：要求**答案区间的中点落在 chunk 内**，而不是
> 「有交集就算命中」。原判据下 chunk（~48s）擦到边界一秒即算命中，偏乐观 ——
> 实测 `multi_hop` 0.938 → 0.750、`joint` 0.562 → 0.375。
> **看检索结论请以严格判据为准**，宽松判据保留仅为与历史数字可比。

**两个结论**：

1. **视觉的收益精确落在「只能靠画面回答」那一类上** —— `visual_only` 相关性

另 V4 有 1 题未正确拒答（拒答率 0.938，其余三版均 1.000）。

### 成本分析（2026-09-13）

早期评测只记录了 **token 数与延迟**，从未折算成费用，**视觉开销也从未纳入对比**。
现在网关层统一记账，`evaluation/eval_cost.py` 可按跑批时间窗口从 `data/usage.db`
核算——**含裁判与视觉，这是第一次拿到完整账单**。

| 方案 | 作答<br>(deepseek) | **裁判**<br>(glm) | 视觉 | 总计 | 每题 | 跑批耗时 |
|---|---|---|---|---|---|---|
| V1 RAG | ¥0.2244 | ¥0.5189 | — | ¥0.7433 | ¥0.0093 | 9.8 min |
| V2 全量 | ¥0.2694 | ¥0.6905 | — | ¥0.9599 | ¥0.0120 | 12.3 min |
| V3 固定视觉 | ¥0.2671 | ¥0.6771 | ¥0.2628 | ¥1.2070 | ¥0.0151 | 5.7 min |
| V4 自主视觉 | ¥0.4776 | ¥0.8227 | ¥0.6366 | ¥1.9369 | ¥0.0242 | 13.2 min |

**三个值得注意的点**：

1. **裁判比作答还贵。** 每个方案里裁判成本都是作答的 1.7~2.3 倍
   （V1：0.5189 vs 0.2244）。评测本身的开销超过了被评测的东西 ——
   因为裁判每题要跑 2~3 次、且提示词里带着完整上下文。
   → **评测成本常被忽略，但它可能才是大头。**

2. **只看「服务一个问题的成本」**（作答 + 视觉，不含裁判）：

   | | V1 RAG | V2 全量 | V3 固定视觉 | V4 自主视觉 |
   |---|---|---|---|---|
   | 每题 | **¥0.0028** | ¥0.0034 | ¥0.0066 | ¥0.0139 |

   **V4 是 V1 的 5 倍。** 视觉是主要开销，且 V4 的总视觉调用（183 次）
   比 V3 的固定调用（78 次）还多 —— "按需调用"省下的，被长尾吃回去了。

3. **视觉单价高且无缓存。** `qwen-vl-plus` 输出 6 元/M 是 `deepseek-v4-flash` 的 3 倍，
   且视觉输入不享受前缀缓存。→ 想降本，优化视觉调用次数比优化 chat 更有效。

> **口径说明**：裁判成本对四个变体同构（同样 176 次调用、同样提示词），
> 因此不影响横向排名；但它的绝对值首次被计量出来了。
> （此前 `gateway.chat()` 自身不记账，裁判与 V1/V2/V3 的作答都没进 usage.db ——
> 该缺口已于 2026-09-13 修复，见下。）

#### 网关记账收口（2026-09-13 修复）

原设计里 `log_usage` 散落在各个调用方（agent / vision / embedding / asr / rag），
**网关自己不记账**。网关本来是「所有模型调用的唯一入口」，记账却没收到这一层，
结果就是「有的路径记了、有的忘了」——`gateway.chat` 直连的调用完全隐形。

现已把记账收进网关，覆盖 `chat` / `chat_with_tools` / 两个流式版本 /
`vision` / `embed` / `asr` / `asr_url`，并删掉调用方那几处（否则重复计数）。
验证：对 agent 跑一题，实际发起的每次调用与 usage.db 的行数一一对应，无重复。

顺带修掉的三个问题：
- **流式调用的用量完全没采集**：`chat_stream` 连 `stream_options={"include_usage": True}`
  都没带，OpenAI 兼容流式默认不返回 usage —— 而流式正是产品的默认交互路径
- **压缩代理的成本隐形**：每次视觉调用后的工具结果压缩走 `gateway.chat`，
  此前从未入账（实测一题 3 次 chat 调用里就有 1 次是它）
- **裁判成本隐形**：所有评测的裁判调用走 `gateway.chat`，同样从未入账

`video_id` 作为可选参数下传：忘了传只会「没归到某个视频」，**不会丢账**。

### 四条关键结论

1. **视觉的收益精确落在「只能靠画面回答」那一类上**
   以 V2 为基线，`visual_only` 相关性 V3 **+0.196**、V4 **+0.259**；
   其余三类（字幕可答 / 跨片段 / 字幕+画面）基本持平或小幅波动。
   **视觉不是万能加分项，它只在需要看画面时才兑现。**

2. **全量字幕优于 RAG，但是「稳定小幅领先」而非「碾压」**
   V2 对 V1：质量 12 项胜 9 / 负 1 / 平 2。优势主要来自跨片段与画面题。
   > 注：数据修正前曾测出「11 项胜 10 项、multi_hop 忠实度 +89%」，
   > 那主要是**错误字幕对 RAG 的伤害远大于对全量字幕**造成的假象。

3. **Agent 自主视觉质量胜出，但更贵更慢**
   V4 在 8 项指标里赢 5 项，且在 `visual_only` 相关性上**优于固定视觉**
   （0.697 vs 0.634）—— 前提是给了它「用户暂停在哪」的上下文。
   代价：延迟 3 倍（21.4s vs 7.0s），每题成本 ¥0.0139 vs ¥0.0066。
   → **Agent 的价值在质量与灵活性，不在这个场景的成本。**

4. **评测本身的开销比被评测的东西还大**
   每个方案里裁判成本都是作答的 1.7~2.3 倍（V1：¥0.5189 vs ¥0.2244）。
   **这一点在做方案选型时最容易被忽略。**

## V5：字幕+暂停帧 vs 原生多模态视频（2026-09-14）

**问题**：既然现在有多模态模型能直接吃整段视频，那「字幕 + 用户暂停的那一帧」
这种轻量方案还有必要吗？

两个档，同数据集、同 80 题、同裁判（`glm-5.3-flash`）、同一轮次跑完：

| 档 | 给模型什么 |
|---|---|
| **V5-frame** | 完整字幕 + **暂停点的那 1 帧原图** |
| **V5-video** | 完整字幕 + **整段视频**（640p，模型自行采样） |

裁判口径两档一致：`--judge-context img`，即**裁判直接看原图**，不读 VL 转述。

### 结果

| 类型 | frame 忠实/相关/引用 | video 忠实/相关/引用 | 延迟 frame→video |
|---|---|---|---|
| single_hop | 0.909 / 0.956 / 0.938 | 0.897 / 0.969 / 0.875 | 10s → 108s |
| multi_hop | **0.947** / 0.934 / 0.938 | 0.872 / **0.997** / 1.000 | 21s → 122s |
| joint | 0.925 / 0.916 / 0.800 | 0.896 / **0.991** / 0.812 | 20s → 103s |
| visual_only | **0.872 / 0.872** / 0.900 | 0.801 / 0.781 / 0.923 | 17s → 107s |
| unanswerable | 拒答 0.938 | 拒答 0.938 | 10s → 73s |

| | frame | video | 倍数 |
|---|---|---|---|
| 平均延迟 | **15.5s** | 102.7s | **6.6×** |
| 总 input token | 352,104 | 20,734,564 | **59×** |
| 缓存命中率 | 71.3% | 86.7% | — |
| **实测费用** | **¥1.88**（¥0.0236/题） | **¥15.80**（¥0.1975/题） | **8.4×** |

### 结论

**原生多模态没有更好 —— 它慢 6.6 倍、贵 8.4 倍，而且在画面题上更差。**

而且差异的**方向是反的**，这一点比总分更有信息量：

- **整段视频赢在「纯文本推理」**：`multi_hop` 相关性 0.997 vs 0.934、
  `joint` 0.991 vs 0.916。整段上下文都在手里，跨片段的整合答得更完整。
- **单帧赢在「画面题」**：`visual_only` 0.872/0.872 vs 0.801/0.781。
  整段视频**没有「该看哪一帧」的锚点**，模型得自己在 10~20 分钟里找那一刻；
  而暂停帧直接把它放在证据上。注意单帧方案的视觉成本几乎为零
  （1 帧 ≈ 300~870 token，整段视频 ≈ 22万~38万 token）。

这正好量化了本项目的立项假设：**「字幕 + 用户暂停的那一帧」在画面题上不输、
甚至好于把整段视频丢给模型，代价却只有 1/8。**

### ⚠️ 解释这份结果时必须带上的三条 caveat

**① frame 档的暂停点用的是题目 `time_start`（＝答案区间起点），相当于给了
「答案在哪一刻」的提示。** 这对画面题是实打实的优势。
辩护：这也是真实产品形态 —— 用户就是在他好奇的那一刻暂停提问的，
系统本来就该知道他在哪。但**不能**把这解读成「单帧的视觉理解能力更强」。

**② 忠实度分数被系统性压低，两档都是。** 见「已知局限」：
裁判看不到标准答案（忠实度 ≠ 正确性），且会惩罚产品提示词鼓励的
「标注过的外部知识」。横向对比不受影响，绝对分不能当「幻觉率」读。

**③ `visual_only` 的分数不能读成「画面答对了百分之多少」。** 见「已知局限」。

### 本轮复盘：跑批本身出的三个问题

这次 V5 大部分时间不是在评测，而是在**修跑批**。三个问题里有两个是同一个根因。

**① 裁判批处理卡死 20 分钟 —— 重试是乘法关系。**
`openai SDK 自带 max_retries(3) × 网关 _with_retry(4) × 裁判梯度(3) × 裁判外层(3)
＝ 最坏 108 次尝试/条`。而每次尝试的代价可能上百秒。
修：`max_retries=0`，重试只保留显式控制的那层。
（复盘详见踩坑记录 #27）

**② 裁判超时沿用了产品侧的 120s。**
裁判是 12000 max_tokens 的思考型生成，reasoning 实测吃 4000~6500 token，
单次要 2~4 分钟 —— 用 120s 等于**每次都在生成中途打断**，
而被打断的那次**已经生成并计费了**。修：单独的 `JUDGE_TIMEOUT=300`。

**③ 同一个超时又坑了 video 档 —— 80 题里 18 题生成失败。**
`LLM_TIMEOUT=120` 还挂在多模态 chat 上，而 video 档要上传整段视频（十几 MB），
整条请求轻松超过 120s，**每条白烧 8 分钟**（120s × 4 次重试）。
判据是**文件大小**不是 token 数：13MB 级的两个视频全挂（各 9/10），
≤11MB 的全过（其中一条 37.6 万 token 反而没事）。
修：`chat()` 加 `timeout` 形参，评测侧传 600s，**产品侧维持 120s**
（产品走流式，120s 只是数据块之间的间隔，本来就是对的）。

> **①②③ 是同一个教训的三次重犯：超时/重试这类"全局常量"，在
> 不同性质的调用路径上必须取不同的值。** 更值得记的是——
> 我在 #27 里已经写下了这条原则，然后只改了裁判一个调用点就收工了。
> 这是踩坑 #22「同类问题只修一半」的第七次。

**④ 顺带修的一个隐患**：结果原来只在**全部跑完（含裁判）之后**写一次，
中途卡住就得整批重跑（已生成的回答、已花的钱全丢）。
改成**每完成一个视频就原子写 `.partial.json`**，最坏只损失卡住的那一题。

## 已知局限（使用时请注意）

| 项 | 说明 |
|---|---|
| **字幕为 B站官方字幕** | 官方 AI 字幕仍可能有少量识别错误（如 `numpy`→`南派`） |
| **部分标注待复查** | 已发现并修正 6 条超出视频时长的标注；可能仍有偏差的（见修订记录） |
| ~~judge 与被评模型同源~~ **已解耦** | 裁判用独立的 `JUDGE_*` 模型（现为 `glm-5.3-flash` / 智谱），**与被评模型（deepseek）不同源**。若 `JUDGE_*` 未配置会回落默认模型并**告警**（此时自评偏差回归，报告需注明） |
| ⚠️ **分数尺度由裁判模型定义** | 换裁判后 **64 题里 42 题的分数变了**（系统性偏移，非抖动；`visual_only` 忠实度 0.53→0.81）。因此：**切换裁判 = 历史数字作废**，且报告里的绝对分数必须连同「谁判的」一起给出 |
| **暂停点假设** | V3/V4 都用题目 `time_start` 模拟「用户暂停位置」，是给系统的一点提示。**`unanswerable` 题的 `time_start` 固定为 0**（约定用 -1/0 表示"无答案区间"），所以该组的 `vision_rate` 含义是「对着视频开头那一帧去求证一个视频里根本没有的东西」，解释时要注意 |
| **生成温度 0.7** | 被评模型用产品真实温度（0.7，有随机性），而裁判是 `temperature=0`。这是刻意的——用产品的真实设置评测才有意义。代价是**版本之间的差异里混着采样方差**，小幅差异（<0.05）不宜当作结论 |
| **「冷启动」跨运行不可信** | provider 侧前缀缓存是**跨运行持久**的，上次跑批跑过同一视频时，本次第一题也会命中缓存。V2 会自检并告警（`cold_not_cached`），成本对比应在同一轮次内比较 |
| **字幕平均仅 4,128 tokens** | 视频 10-20 分钟，是全量字幕方案最有利的场景，长视频结论不能直接外推 |
| ⚠️ **`visual_only` 的忠实度/相关性不可作为画面正确性的依据** | 见下 |
| ⚠️ **忠实度 ≠ 正确性** | 裁判只看「参考材料」，**看不到标准答案**。答对了但材料里没写，照样判无依据 —— 见下 |
| ⚠️ **忠实度裁判会惩罚「标注过的外部知识」** | 产品提示词**鼓励**模型补常识，裁判**一律**判无依据 —— 见下 |

### ⚠️ `visual_only` 分数的可信度限制

**裁判（LLM-as-judge）拿到的参考材料是「字幕 + 画面描述文本」，它从没见过图片本身。**
所以它只能核对「回答是否与画面**描述**一致」，而不是「回答是否与**画面**一致」：

- 描述模糊 → 模糊但听起来合理的回答就能过关（**分数虚高**）
- 描述写错 → 正确的回答反被判「无依据」（**分数虚低**）

而实测已确认画面描述**确实会丢细节**（小号图注、色块里的数字、括号框住哪几行，
`qwen-vl-plus` 读不稳定）。因此该偏差是**实际发生**的，不是理论担忧。

**结论：`visual_only` 的分数可用于横向比较四个变体的相对高低，但不能理解为
「画面答对了百分之多少」。** 修复方向见待办（多模态裁判 / 人工抽查）。

> **V5 起这条已部分解决**：V5 的记录带 `judge_images`，裁判**直接看原图**
> （`--judge-context img` 为默认）。V1~V4 不带该字段，行为不变，所以上面这段
> 对 V1~V4 仍然成立。
>
> 但要注意踩坑 #19：裁判**不会自动**把随附的图当成参考材料 ——
> `FAITHFULNESS_PROMPT` 写的是「只依据参考材料判断」，它会把这个「参考材料」
> 理解成 user 消息里那段**文本**，附上的图被当作噪音。
> 必须在 user 消息里显式声明「随附画面同样算参考材料」，否则画面题的正确回答
> 会被系统性判成无依据（实测：同一断言不加这句 0.0，加了 1.0；
> `visual_only` 忠实度被压到 0.486，逐条人工核对 5 条里 4 条其实是对的）。

### ⚠️ 忠实度口径的两条系统性压低（V5 期间确认，**影响 V1~V5 全部**）

这两条**不是 bug，是口径张力**，但会让**所有**绝对忠实度分数偏低，
报告里必须连同结论一起给出，否则「忠实度 0.85」会被误读成「15% 的内容是编的」。

**① 忠实度 ≠ 正确性：裁判看不到标准答案。**

`FAITHFULNESS_PROMPT` 只给裁判「参考材料 + 回答」，**不给 `reference_answer`**。
于是「答对了、但材料里没写」会被判成「无依据」。

实例（V5-video 第 5 题）：问画面里的机器人型号，模型答对了（`reference_answer` 里
就是「大黄蜂」），但**字幕没提、那一帧画面也没标注**，裁判无从核对 → 判无依据。

这不是裁判判错，而是忠实度这个指标**本来就不衡量正确性** ——
它衡量的是「回答是否忠于给定材料」。正确性该看 `relevancy`（那一栏裁判是能看标准答案的）。

**② 裁判惩罚产品提示词鼓励的行为。**

`AGENT_SYSTEM_PROMPT` 明确**鼓励**模型补充「标注过的外部知识」
（如「这是 Pre-LN 变体」「这是正弦/余弦位置编码」）。但忠实度裁判的判据是
「参考材料里没有的即视为无依据」，**一律扣分**。

两边定义直接冲突：产品希望模型像个懂行的助教，评测却在惩罚它这么做。
实测这类被扣分的断言在 V5 两个档里都出现了，且**模型加得越主动扣得越多**。

**影响面：** 两条都对 V1~V5 一视同仁，因此**横向排名不受影响**
（同一把尺量所有变体）；受影响的只有**绝对分数**，而且是**系统性偏低**。
修复方向：让裁判能区分「编造」与「标注过的外部知识」（改 prompt 或加一个
`external_knowledge` 字段单列），或把忠实度拆成「忠于材料」+「事实正确」两个指标。
**在修之前，不要拿忠实度分数直接当「幻觉率」。**

### 踩坑与修正（V4 期间发现的两个问题）

**① Agent 有工具，却没有「当前在哪」的上下文。**
首次 V4 结果显示画面题比 V3 又慢 8 倍又更差。逐次调用分析发现：
16 道画面题 222 次调用，**只有 5 题看过用户暂停的那一帧**；最极端一题答案在第 14 秒，
它把 0~840 秒整段扫了一遍（44 次调用 / 208 秒 / 0 分）。
根因是 `analyze_frame` 的 `timestamp` 是**必填参数，但没有任何地方告诉过模型用户在哪**。
修复：注入 `<player_state>` + `timestamp` 改为可选、默认当前暂停点。
**效果：那题 44 次 → 2 次，画面题看对暂停点的比例 5/16 → 15/16。**
（这是产品 bug，不只是评测问题——真实用户问画面问题时 Agent 同样在瞎扫。）

**② 评测脚本自身的 bug 曾被当成「Agent 能力差」。**
一次 V4 跑批 9 分钟出完整报告，实际 **23/80 题的回答里写着「截帧工具持续报错」**——
那次运行画面题根本没有画面。根因是模块级 `import asyncio` 与函数内遗留的
`import asyncio` 冲突，导致前面所有 `asyncio.to_thread` 报 `UnboundLocalError`。
**已给评测加跑批健康检查**：视觉失败率 >10% 直接判定结果不可信并写进 `health` 字段。

## 复现方式

```bash
# 评测集
python evaluation/build_dataset.py          # 从 markdown 评测集构建 dataset.json

# V1 纯字幕 RAG
python evaluation/eval_retrieval.py         # 检索层（约 3s）
python evaluation/eval_generation.py        # 生成层（约 14min，消耗 token）

# V2 全量字幕注入（不检索）
python evaluation/eval_full_context.py      # 约 17min

# V3 全量字幕 + 固定视觉
python evaluation/eval_v3_full_vision.py    # 约 9min（视频级并行，含抽帧）

# V4 全量字幕 + Agent 自主调用视觉
python evaluation/eval_v4_agent.py          # 约 15min

# 成本核算（按跑批时间窗口从 data/usage.db 捞账）
python evaluation/eval_cost.py --last-log eval_v4_agent --label "V4" --questions 80
# 或显式指定窗口
python evaluation/eval_cost.py --start "2026-09-13 02:59:09" --end "2026-09-13 03:14:11"

# 辅助
python evaluation/retry_failed.py           # 重判失败的裁判记录
```

**抽帧说明**：V3/V4 的画面评测优先使用 `项目文档/评测/视频/` 下的本地视频文件，
找不到时回退到从 URL 拉流。

**日志**：每次跑批都会在 `evaluation/logs/` 下留一份独立日志
（`{脚本名}_{时间戳}.log`，已 gitignore），记录每题用了哪个时间点、成功与否，
便于事后追溯。跑批结束会打印**健康检查**——视觉失败率 >10% 时会明确提示
「结果不可信」，而不是照常出报告。

**并行说明**：V3/V4 均为**视频级并行**（8 路），视频内仍顺序提问以保住字幕前缀缓存。
早期版本为保缓存写成完全串行，一次跑批要 90 分钟——实测字幕仅 2.6~6k tokens，
缓存省下的钱远小于串行的耗时，属于算错账。
